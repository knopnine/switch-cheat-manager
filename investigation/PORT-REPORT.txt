SwitchCheatCodeManager: web port investigation
Date: 2026-10-21 (Asia/Jakarta)
Status: analysis only. No port implementation, build, test suite, target launch, or deployment was performed.

DECISION

A web port can reproduce the cheat-management, metadata, formatting, comparison,
and code-generation workflows. A browser alone cannot provide identical Windows
integration. If automatic drive scanning and opening the operating system's file
manager are required, add a local companion service behind the web interface.

Recommended target: a local-first browser application with direct folder access
where supported, ZIP import/export as a fallback, and an optional local companion
for strict desktop integration. Keep the same cheat files and folder layout.
Feature parity should mean equivalent successful workflows and compatible output;
known defects should be documented as intentional corrections.

FUNCTIONAL PARITY INVENTORY

1. Library import and browsing
   Open a library containing Title ID directories, a game directory, or its
   cheats directory. Filter games by display text. Show optional game images
   and version labels; order Build ID entries by mapped version.
   Sources: Helper/MainHelper.cs:112-179; WinForm/MainForm.cs:261-417,484-553.
   Browser: feasible through selected-folder or imported virtual file tree.

2. Game and build management
   Create a game directory, metadata file and initial cheat. Add/remove/rename
   Build ID files; update the associated version mapping. Rename game metadata.
   Sources: WinForm/MainForm.cs:723-1058,1455-1502.
   Browser: feasible; direct disk mutation needs permission to a selected folder.

3. Version index editing
   Edit, add, delete and order Build ID/version mappings.
   Sources: WinForm/EditVersionIndexForm.cs:137-209.
   Browser: feasible.

4. Raw cheat editing and saving
   Read text, edit, save over the source, or Save As. Highlight headers and
   subsection markers. Navigate from cheat names to editor positions.
   Sources: WinForm/MainForm.cs:420-479,808-821,1131-1209,1428-1443.
   Browser: feasible, with direct-save adapter plus download fallback.

5. Parsing and formatting
   Recognize ordinary headers, optional title-only header, master block, brace
   comments and section boundaries. Uppercase instruction words and standardize
   spacing; normalize some header strings. Bulk formatting also uppercases IDs.
   Sources: CheatCode/CheatFile.cs; CheatBlock.cs; CodeLine.cs; MasterBlock.cs;
   WinForm/MainForm.cs:585-649.
   Browser: feasible. Raw input must be retained independently of parsed output.

6. Sections and enabled markers
   Add/rename sections, navigate to them, and toggle :ENABLED header suffixes.
   These are text changes for compatible overlays, not live console activation.
   Sources: CheatCode/SubCheat.cs; CheatBlock.cs:144-168;
   WinForm/MainForm.cs:1065-1130,1211-1330,1623-1663.
   Browser: feasible.

7. Comparison
   Select two Build ID files for one game and highlight line/character changes.
   Source: WinForm/CodeCompareForm.cs:175-275.
   Browser: feasible, but original implementation is incomplete.

8. Code builder
   Eleven operation panels cover opcode families 0-9 and A: static memory write,
   conditional comparison, End/Else, loops, register load from static/memory,
   static store through register, legacy arithmetic, button activators, register
   arithmetic and register-to-memory store. Append generated text, clear output,
   and copy to clipboard. This is not full coverage of all modern cheat opcodes.
   Sources: WinForm/CodeBuilderForm.cs:43-84,131-153; SubView/*.cs.
   Browser: feasible; preserve widths, bitmasks, registers and zero padding.

9. Number tools
   Hex/decimal conversion and a hex add/subtract/multiply calculator.
   Source: WinForm/CodeBuilderForm.cs:100-128,161-201.
   Browser: feasible using BigInt with explicit ranges/signedness. Keep IDs as
   strings; never parse 64-bit IDs and values through JavaScript Number.

10. Images and local game metadata
    Select/attach preview images; prefer English/Chinese/Japanese image names.
    Optional library-root GAMES.md supplies local game name recognition.
    Sources: Helper/ActionHelper.cs:36-65,104-126;
    Helper/MainHelper.cs:203-239; CheatCode/Games.cs:15-35.
    Browser: feasible. The application does not establish an online game database.

11. Output copy
    Copy selected stored cheat to <output>/<TID>/cheats/<BID>.txt. Copy a game
    recursively with all its files and overwrite matching destinations. Folder
    copy merges; it does not remove unrelated destination files.
    Sources: WinForm/MainForm.cs:1504-1579; Helper/ActionHelper.cs:217-248.
    Browser: feasible inside user-granted folders. ZIP export preserves the
    intended directory layout but requires the user to extract it afterward.

12. Settings and localization
    Default input/output folders, four highlight colors, English/Simplified
    Chinese UI and preferred preview-image language. Original storage is a custom
    line-prefix settings.ini file; browser storage can replace the persistence
    mechanism with optional compatible settings import/export.
    Sources: CheatCode/ConfigSettings.cs:16-35,68-181;
    WinForm/SettingsForm.cs:187-217; Constant/Constants.cs:32-51.

13. Desktop integration
    Scan mounted drives for atmosphere/contents when output is unavailable.
    Open directories through Windows Explorer.
    Sources: CheatCode/ConfigSettings.cs:88-110; Helper/ActionHelper.cs:21-25.
    Browser: cannot promise these host operations. Use explicit folder selection
    or a local companion service for corresponding host integration.

14. FTP
    FtpUtility only lists remote directory details. Scoped search found no UI
    wiring or callers and no established upload/download workflow.
    Source: Model/FtpUtility.cs:15-40; all .cs source was available for search.
    Exclude FTP transfer from the existing parity promise. It can be a separate
    future feature, requiring a suitable transport outside a plain browser.

COMPATIBLE DATA FORMAT

  <library>/
    <16-hex-Title-ID>/
      Game Name.txt              (BuildID<TAB>version rows)
      Game Name.jpg              (optional; PNG also recognized)
      cheats/
        <16-hex-Build-ID>.txt

Headers and sections include [Cheat name], [Cheat name:ENABLED], {Mastercode},
brace comments, [--SectionStart:Name--] and [--SectionEnd:Name--]. Section-marker
blocks contain the dummy instruction 00000000 00000000 00000000. Existing raw
text, unknown instruction families, comment order, encoding and line endings
should survive an open/save cycle unless formatting is explicitly requested.

IMPORTANT LIMITATIONS AND DEFECTS

- Validation checks textual shape: one to four groups of eight hex digits and
  some document structure. It does not prove instruction semantics, correct
  addresses, compatibility with a game version, or that a cheat works.
  CheatCode/CodeLine.cs:68-100.
- Ordinary cheats have a 64-line check; subsection parsing does not consistently
  apply it. Treat this as original behavior, not an authoritative platform rule.
  CheatCode/CheatFile.cs:71-75,106-110,165-169; SubCheat.cs:35-62.
- TerminatorForm emits literal 2X000000 for both selected End and Else paths.
  SubView/TerminatorForm.cs:23-29. Released DLL method 0x06000124 statically loads
  the same format string and X literal, corroborating the source defect.
- Family 9 RHS registers A-F are encoded using decimal SelectedIndex text.
  SubView/ApplyArithmeticOperationForm.cs:64-70. Source defect; not runtime-tested.
- Comparison has an empty right-longer branch and misses some trailing lines.
  WinForm/CodeCompareForm.cs:175-275. Source defect; not runtime-tested.
- Entire game deletion immediately deletes recursively without a confirmation
  in that path. WinForm/MainForm.cs:823-834,1448.
- Selected-file export copies disk content without saving the current editor.
  WinForm/MainForm.cs:1542-1579.
- Save warns about size after writing, using rounded KiB >=32. It does not guard
  the write. WinForm/MainForm.cs:458-473.
- Reformatting moves comments before instructions and changes header spelling;
  a missing title-only header can yield []. Some metadata writers use ASCII.
  CheatCode/CheatBlock.cs:106-156; CheatFile.cs:207-225;
  Helper/ActionHelper.cs:171-189.
- Malformed headers can leave null Codes and crash later serialization.
  CheatCode/CheatBlock.cs:96-103; CheatFile.cs:165.
- ASMHelper only describes families 0-4; its current builder result is discarded.
  Do not claim an existing full decompiler or cheat explanation feature.
  Helper/ASMHelper.cs:29-164; WinForm/CodeBuilderForm.cs:95-97.

RECOMMENDED ARCHITECTURE (PROPOSAL, NOT IMPLEMENTED)

Use TypeScript for a platform-independent cheat/document engine. A React UI with
CodeMirror is a reasonable editor choice, subject to dependency selection during
implementation. Separate parsing, serialization, validation, opcode generation,
version metadata and comparison from storage and UI components.

Keep a raw document plus a structured view with source ranges. This supports
reliable navigation and targeted changes without rewriting unrelated content.
Use strings for identifiers and fixed-width words and BigInt for arithmetic.

Storage adapters:
  1. Browser directory adapter: user-selected input and output folders; direct
     changes only after permissions are granted. Verify permissions on reopening.
  2. ZIP/virtual-tree adapter: portable import/export fallback and downloadable
     single files. ZIP operations are additions to ease browser use.
  3. Optional localhost companion: drive discovery, robust host file operations,
     Explorer integration and future network transports if required.

Local browser persistence can retain preferences, drafts and permitted folder
handles. Add an offline application shell. Core editing needs no cloud account,
uploaded cheat files, or remote database. These are recommended design choices,
not observed original requirements.

If exact OS integration is mandatory from the first release, choose the local
companion architecture from the start. Installing a PWA alone does not remove
browser permission or host integration limits.

SUGGESTED DELIVERY SEQUENCE AFTER IMPLEMENTATION IS AUTHORIZED

1. Freeze the parity checklist against release v1.1.0 + inspected main; record
   intentional deviations for the defects above and browser integration changes.
2. Create representative fixtures for titles, masters, comments, sections,
   duplicate names, enabled flags, malformed input, unknown words and versions.
3. Implement and verify parser/serializer, metadata and builder before tying
   them to editor interactions. Check all eleven families and boundary values.
4. Build library browsing, editing, management, comparison, settings and images.
5. Add direct-folder operations and fallback exports. Verify copy merge rules,
   permission denial, removed media, interrupted writes and unsaved changes.
6. Verify intended workflow equivalence and output compatibility. Compare the
   original against fixtures in a later bounded runtime investigation if needed.

The last step would require launching the original; no runtime parity is claimed
in this report. Browser compatibility, real SD-card writes, rendering/performance,
complete game-code validity and source-to-binary equivalence remain unverified.
